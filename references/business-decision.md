# Business Decision

China Legal OS 的终点不是"解释法律"，是**帮企业做出法律风险可控的商业决策**。

判断标准（用户定义的最终标准）：
> 一个优秀企业法务看到这个结果以后，是否愿意基于它继续工作。

一份止步于"存在法律风险，建议谨慎"的输出，答案是否。

---

## 1. 必答七问

**缺一不可。** 任何一问答不了，就说明为什么答不了以及需要什么才能答。

### 1. 能不能做？
`可以 / 有条件可以 / 不建议 / 不能`

四选一，不要模糊。"不能"只用于 BLACK 和违法情形。

### 2. 怎么做风险最低？
具体路径，不是原则。不是"加强合同管理"，是"把付款节点从预付 100% 改为 30/40/30，并把验收标准写进附件三"。

### 3. 如果业务坚持必须做，怎么办？
**这一问最重要，也最常被跳过。**

法务说"不建议"而业务照做，是企业里每天发生的事。真正有用的法务会准备好第二方案：在必须做的前提下，怎么把风险降到最低、怎么留证据、怎么设置止损点。

拒绝回答这一问 = 把风险留给业务方独自承担。

### 4. Fallback 是什么？
首选方案被拒绝时的退让路径，以及退让的底线在哪。

### 5. 什么条件触发升级？
可判定的条件，不是"如果情况严重"。见 `risk-rating.md` §5。

### 6. 谁需要审批？
岗位。`company/company-legal-context.md` 未填写时用默认升级链并标注为默认。

### 7. 今天应该做什么？
**至少一条**，具体到：做什么 · 谁做 · 什么时候前 · 需要什么材料。

时限敏感动作（证据固定、时效、期限、对方回签期）必须置顶并写明"不做会怎样"。

## 2. 缺 company context 时

**不得推断**。不得因为公司是 SaaS 就假设"风险偏好中等"，不得因为金额小就假设"总经理不用管"。

处理方式：
1. 交付物抬头写 `Review Basis: 通用商业标准（未加载公司法务上下文）`
2. 升级链用默认占位，并标注为默认
3. 末尾列出"若补充以下信息，本结论会改变"，具体到字段

```
【若补充以下信息，本结论会改变】
- 公司对该类合同的授权审批金额门槛 → 决定本案是否需要 E4 审批
- 是否有既定的责任上限标准立场 → 决定第 12 条是"偏离"还是"符合"
- 与该供应商的既往合作情况 → 影响谈判姿态和让步空间
```

## 3. 输出骨架

```
【结论】
可以做，但需先解决第 12 条。

【建议路径】
1. 本周内向对方提出第 12 条修改（文本见审查意见）
2. 同时准备 fallback：三倍合同总价上限 + 排除间接损失
3. 若对方全部拒绝，转 E4 决策：接受风险签署，或换供应商

【如果业务必须本周签】
可以签，但需同时做三件事：
  a. 采购负责人书面确认已知悉无上限赔偿风险（内部留痕）
  b. 在首批交付前完成第三方 IP 排查，把最可能触发索赔的场景排掉
  c. 向保险经纪询价，确认现有责任险是否覆盖此类第三方索赔
这三件事把"不可控敞口"变成"已知且部分对冲的敞口"。

【升级】
E2 法务负责人 —— 因赔偿责任无上限，超出可接受区间
需要材料：合同全文、本审查意见、对方历史合作记录
时限：本周四前，对方要求下周一回签

【今天】
1. 把第 12 条修改意见发给对方法务          法务经办    今天下班前
2. 向采购确认是否可接受推迟一周签署        法务经办    今天下班前
3. 启动第三方 IP 排查（若确定要签）        产品 + 法务  时限敏感，需 5 个工作日
```

## 4. 语言

写给业务方和管理层看，不是写给法务同行看。

- 先给结论，后给理由
- 法律术语后面跟一句人话解释后果
- 金额、时间、责任人写具体值，不写"较大""尽快""相关人员"
- 不要在决策文件里展开法律论证——论证放在支撑文件里，这里只放决定和依据摘要

---

## 5. 禁止

| 禁止 | 为什么 |
|---|---|
| 止步于"存在风险，建议谨慎" | 没有决策价值 |
| 跳过第 3 问 | 把风险留给业务方独自承担 |
| "建议咨询专业律师"作为结论 | 不是动作。见 `risk-rating.md` §5 |
| 推断公司风险偏好、审批链、商业优先级 | 见 §2 |
| 只给一个方案没有 fallback | 谈判中一定会用到 |
| "今天应该做什么"写成"持续关注" | 不可执行 |
