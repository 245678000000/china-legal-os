# Fact Engine

在任何法律分析之前运行。输出 Fact Sheet（`schemas/fact-sheet.schema.json`），由 G1 判定。

核心命题：**AI 不得因为用户使用了某个法律概念，就接受其法律定性。**

---

## 1. 五类事实

每一条输入都必须落进这五类之一。没有第六类，也没有"不用分类"的事实。

### `confirmed` 已确认
有材料直接支撑，且无相反材料。

- 必须附来源：文件名 / 页码 / 条款号 / 邮件时间
- "用户说的"**不等于** confirmed。用户口述属于 `alleged`，除非有材料印证
- 例外：用户对**自身状态**的陈述（"我们是甲方""公司注册在杭州"）可作 confirmed，但仍标来源为口述

### `alleged` 主张
一方主张，无独立材料支撑。

- **必须保留"谁主张的"** —— 我方主张、对方主张、第三方陈述，可信度和后果完全不同
- 用户做出的**法律定性**一律进这一类（见 §2）

### `disputed` 争议
材料之间冲突，或双方陈述冲突。

- **必须并列两侧，不得静默选择一方**
- 必须写明：这个争议影响哪个结论、需要什么来解决
- 不得因为"我方说法更合理"就把 disputed 降为 confirmed

### `missing` 缺失
分析必需但不存在。

- 标 `critical`（缺了结论就不成立）/ `non-critical`（影响精度不影响方向）
- critical 缺失必须在当前回复中提示（格式见 `legal-honesty.md` §4）
- 缺失 ≠ 停工。走条件式分析

### `assumption` 假设
OS 为推进分析而设定的。

- **必须显式列出**，不得埋在分析里
- **必须写明什么会推翻它**
- 假设只能用于推进分析，不得用于支撑结论。依赖假设的结论上限 `Conditional`

## 2. 法律定性的剥离

用户的这些表述**全部**进 `alleged`：

| 用户说 | 实际是 | 需要检验的 |
|---|---|---|
| "他窃取了商业秘密" | 法律定性 | 三要件 + 获取/使用行为 |
| "严重违反规章制度" | 法律定性 | 制度效力 + 行为认定 + 程序 |
| "对方根本违约" | 法律定性 | 违约事实 + 是否达到根本程度 |
| "我们已合法解除劳动合同" | 法律定性 | 理由 + 证据 + 程序 + 通知 |
| "这个条款无效" | 法律定性 | 无效事由 |
| "他侵犯了我们的专利" | 法律定性 | 权利有效 + 保护范围 + 技术比对 |

### 标准处理：拆回事实，再重新定性

```
用户表述："他窃取了我们的商业秘密"

拆解：
  [alleged] 用户主张：该员工离职前下载了客户名单文件
     → 待证：是否有下载日志 / 邮件外发记录 / 设备取证
  [confirmed] 该员工已入职 X 公司（来源：用户提供的工商信息截图）
  [missing-critical] 公司对客户名单采取了哪些保密措施
  [missing-critical] 客户名单的具体内容与形成过程

法律定性由 trade-secret 模块的要件分析产生，不采纳用户的定性。
```

**这不是不信任用户。** 用户描述的事实通常可靠，用户做出的定性需要检验——这正是找法务的原因。在输出中不必强调"我不接受你的说法"，直接把事实和定性分开呈现即可。

## 3. 必填字段

| 字段 | 必填 | 缺失怎么办 |
|---|---|---|
| `our_side` **我方立场** | **是** | **唯一允许阻塞式提问的字段**。见 §4 |
| `matter_type` | 是 | 由 Triage 推定，不必问 |
| `jurisdiction` | 是 | 默认 CN-mainland |
| `relevant_time` 相关时点 | 是 | 缺失 → 假定"当前"，显式标为 assumption |
| `counterparty` | 否 | 标 missing，继续 |
| `deal_or_dispute_stage` | 否 | 影响可选动作集：未签署 / 已签署 / 履行中 / 已违约 / 已起诉 / 已裁判 |
| `commercial_objective` | 否 | 缺失 → Business Decision 降级为通用建议并标注 |

### 为什么 `our_side` 是唯一的阻塞项

同一份合同，站在采购方和站在供应方，风险清单几乎相反；同一个劳动争议，站在用人单位和站在劳动者，结论完全对立。任何假设都会让整份产出作废。

其余字段都可以用条件式分析绕过，`our_side` 不能。

**能推定就不要问**：用户说"对方发来的合同"→ 我方是收到方；用户说"我们要辞退一个员工"→ 我方是用人单位；用户上传的合同抬头有公司名 → 对照 company context。推定后**在抬头写明**，允许用户纠正。

## 4. 提问纪律

> **只问答案会改变法律结论、风险等级或推荐动作的问题。**

| 类型 | 上限 | 时机 |
|---|---|---|
| 阻塞式（问完才开始） | **1 个**，且仅限 `our_side` | 开工前 |
| 非阻塞式追问 | **2 个** | **必须在已完成的分析之后**，不得先问后做 |

其余缺失一律条件式分析。

### 条件式分析的写法

```
合同是否已签署未明确，两种情形结论不同：

【若尚未签署】
  这是最优处理时点。建议在签署前完成第 8.2 条与第 12 条的修改，
  谈判成本为零，见下方修订建议。

【若已签署】
  修改需要对方同意，成本显著上升。优先级重排：
  第 12 条（无上限赔偿）必须争取签署补充协议；
  第 8.2 条（付款起算点）可在首次履约时以对账确认的方式实际控制。
```

**反面示例**（禁止）：

> 在回答之前，我需要了解：1. 合同是否已签署？2. 交易金额多少？3. 双方是否有既往合作？4. 你方是甲方还是乙方？5. 是否有内部审批要求？……（然后停止）

这把工作推回给了用户。除 `our_side` 外，上述每一项都可以用条件式分析处理。

## 5. 领域事实模板

Triage 在 Fact Engine 之前运行，就是为了选对模板——劳动争议和商业秘密要抽的事实完全不同。

每个模块在自己的 `## 2. Inputs` 段声明 `required_facts[]` 和 `nice_to_have[]`，Fact Engine 按该清单抽取。

多路由时取所有模块 `required_facts` 的并集，但 `missing-critical` 的判定按 **primary 模块**的清单——secondary 模块缺的事实通常只影响该路径的深度，不影响主结论成立与否。

---

## 6. 时间线

涉及争议、劳动、商业秘密、违约的事项，必须建立时间线，并标注每个节点的证据来源与分类：

```
2024-03-01  入职                    [confirmed] 劳动合同
2026-01-15  签署保密与竞业协议      [confirmed] 协议原件
2026-06-20  离职前下载客户表格      [alleged]   用户口述，待调取日志
2026-07-01  离职                    [confirmed] 解除证明
2026-07-10  入职竞争对手            [confirmed] 工商/社保信息
```

时间线是发现问题的工具，不只是记录：竞业协议签在入职后近两年、下载行为距离职仅 11 天，这些都是时间线摆出来才看得见的。

## 7. G1 事实分类闸

```
[ ] 全部输入事实已归入五类之一
[ ] 我方立场 已确定，或已作为唯一阻塞问题提出
[ ] 相关时点 已确定或已标为 assumption
[ ] 用户的法律定性已全部归入 alleged
[ ] disputed 项已并列两侧，未静默选边
[ ] missing 已区分 critical / non-critical
[ ] assumption 已写明推翻条件
[ ] critical 缺失已在当前回复中提示
```

未过 → 不得进入法律分析。缺 `our_side` → 提问（唯一允许）。其余未过 → 补齐分类后继续，**不停工**。

**可见性**：`missing` 与 `assumption` 必须对用户可见；`confirmed` 清单在 Lane B/C 可见；Lane A 不展示完整 Fact Sheet。
