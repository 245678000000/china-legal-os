# Legal Reasoning

不做法律科普。分析路径固定：

```
Issue → Rule → Elements → Facts → Evidence → Counterarguments → Conclusion
```

**关键结构：Reasoning 不直接输出结论，它输出要件。** 要件交给 Evidence 评估，再回来合成结论。见 §3。

---

## 1. 八个共享推理原语

各模块的领域分析都由这八个动作组合而成。写模块 workflow 时引用原语名，不要重复解释推理方法。

| # | 原语 | 做什么 | 常见错误 |
|---|---|---|---|
| **P1** | **要件拆解** | 把一条规则拆成必须逐个满足的要素 | 拆得太粗（"构成侵权"），或漏掉程序性要件 |
| **P2** | **请求权基础定位** | 找到"谁基于什么可以向谁主张什么" | 只找到一条就停。同一事实常有多条基础，成立难度不同 |
| **P3** | **涵摄** | 把具体事实套进要件，逐个判断满足与否 | 泛泛说"符合条件"而不指明是哪个事实满足了哪个要件 |
| **P4** | **解释** | 文义 → 体系 → 目的，按此顺序 | 直接跳到目的解释来支持想要的结论 |
| **P5** | **类比与区分** | 与已知规则或情形比较，说明为何相同或不同 | 无检索源下把"我记得有类似案例"当作类比（违反 R3） |
| **P6** | **举证责任分配** | 每个要件由谁证明，证不出来谁承担不利后果 | 分析完法律就结束，不问谁举证 |
| **P7** | **反面论证** | 站在对方立场找最强反驳 | 写成"虽然对方可能主张 X，但我方显然占优" |
| **P8** | **结论强度标定** | 四元 min 规则，并写明封顶项 | 给一个笃定的结论，或给一个"可能也可能不"的废话 |

## 2. Issue → Rule → Elements

### Issue

争点必须是**可判断真假的具体命题**，不是话题。

❌ "客户名单的法律保护问题"
✅ "本案客户名单是否构成《反不正当竞争法》意义上的商业秘密"
✅ "在未签署书面竞业限制协议的情况下，公司能否要求前员工承担竞业义务"

一个事项通常有 2-5 个真正的争点。超过 8 个说明拆得太细，把要件当成争点了。

### Rule

写规则内容，不是写条号（`source-policy.md` R2）。

格式：`规则内容（谁在什么条件下可以/必须做什么，法律后果是什么）` + `[官方法源-未核验]` + `（法律名称，条号未核验）`

### Elements

拆到**可以单独判断真假**为止。每个要件独立成行，各自带举证责任。

```
争点：本案客户名单是否构成商业秘密

要件 E1  不为公众所知悉        举证责任：我方
要件 E2  具有商业价值          举证责任：我方
要件 E3  权利人采取了相应保密措施  举证责任：我方
```

三个要件的举证难度差异极大，**必须分开评估**——合在一起写"构成商业秘密"会掩盖掉 E3 通常是最难的那个。

## 3. Reasoning ⇄ Evidence 耦合回路

这是全 OS 最关键的结构。**不是两个阶段，是一个回路。**

```
Reasoning  →  Elements[]              每个要件是一个待证命题
              ↓
Evidence   →  逐要件评估              举证责任 / 现有证据 / 强度 / 缺失 / 下一步
              ↓
Reasoning  →  涵摄 → 反面论证 → 结论
              ↓
           四元 min 规则 → 结论确定性 + 封顶项
```

### 为什么必须是回路

单向管线（先出结论，再补证据）在结构上无法通过这个检验：

> 法律分析完全正确，但证据不足时，系统是否会主动降低结论确定性？

如果结论已经写完再看证据，模型会倾向于**为已有结论找证据**，而不是**让证据决定结论**。

### 合成规则

```
结论确定性 = min( 法律确定性, 证据充分度, 事实确认度, 法源核验度 )
```

**必须写出封顶项**：

> **结论**：客户名单构成商业秘密的可能性存在，但目前不能确认。`Conditional`
> **封顶项**：证据充分度（E3 保密措施）。E1、E2 有材料支撑；E3 目前只有一份未见签收记录的保密制度，
> 若能提供员工签收表或系统权限日志，整体可升至 `Probable`。

## 4. Counterarguments（P7）

**每个 High/Critical/BLACK 结论都必须过。** 完整规程见 `red-team.md`，此处是最低要求：

1. 对方最强的一个反驳是什么
2. 哪些事实对我方不利
3. 我方证据链最薄弱的一环在哪
4. 有没有另一种法律解释导向相反结论
5. **结论是否需要下调**（必答，不能跳过）

写作纪律：用对方律师的口吻写反驳，不要边写边打折。
❌ "对方可能主张客户信息可公开获得，但我方名单包含交易习惯，显然不同。"
✅ "对方会主张：这些客户的名称、联系方式可通过公开渠道检索获得，名单本身不具有秘密性；我方主张的'交易习惯、价格底线'部分，需要证明确实记载于名单之中，而目前提交的表格是否包含这些字段尚不清楚。"

---

## 5. Conclusion

结论必须包含四件事，缺一不可：

1. **结论本身**（可判断真假的命题）
2. **确定性标签**（五级之一）
3. **封顶项**（哪一元封的顶）
4. **提升路径**（拿到什么就能升级）

```
结论：公司以"严重违反规章制度"为由解除劳动合同，目前存在较高被认定为违法解除的风险。Conditional

封顶项：证据充分度。
  - 法律要件清晰（制度有效 + 行为构成严重违纪 + 程序合法）
  - 制度文本存在，但未见民主程序记录与员工公示/签收证据
提升路径：
  - 提供职工代表大会或全体职工讨论记录 → 制度效力要件可达 Probable
  - 提供员工手册签收表 → 公示要件可达 Confirmed
  - 两者齐备后，整体结论可达 Probable
若均无法提供：不建议以此理由解除，应转向协商解除路径（见 business-decision）
```

## 6. 禁止事项

| 禁止 | 为什么 |
|---|---|
| 只列法条名，不写规则内容 | 违反 R2，且对读者无价值 |
| 只给结论不给要件 | 读者无法验证，也无法知道哪一环可以补强 |
| 要件拆解后不做举证责任分配 | 企业法务最常见的失败是举证不能，不是法律理解错 |
| 结论确定性高于证据支撑 | 违反四元 min 规则，G3 会拦截 |
| 反面论证写成自我辩护 | 见 §4 |
| 用"司法实践中一般认为"支撑关键结论 | 无来源的权威腔。要么给依据，要么标 `Unverified` |
| 自造案例做类比（P5） | 违反 R3。改为输出检索指引 |
| 把要件当争点，拆出十几个"争点" | 争点是可独立判断的法律问题，要件是争点内部的构成元素 |
